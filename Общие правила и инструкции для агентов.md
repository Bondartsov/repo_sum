## 1. Введение и Цель Документа

### 1.1 Назначение
Настоящий документ устанавливает единые стандарты и правила работы для всех агентов (AI-помощников) в проекте repo_sum. Цель - обеспечение консистентности, качества кода и эффективной разработки.

### 1.2 Область Применения
Инструкции применяются ко всем видам работ:
- Разработка нового функционала
- Рефакторинг существующего кода
- Написание и обновление документации
- Тестирование и отладка
- Архитектурное проектирование

### 1.3 Обязательность Соблюдения
**Все агенты ОБЯЗАНЫ следовать данным инструкциям без исключений.** Отклонения допускаются только с явного одобрения технического лидера проекта.

## 2. Основные Правила Работы Агентов

### 2.1 Обязательное Изучение Документации
**ПЕРВЫЙ И ОБЯЗАТЕЛЬНЫЙ ШАГ** перед любой работой:

1. Изучить **[ROADMAP.md](ROADMAP.md)** - главный документ проекта
2. Ознакомиться со всей системой **[.clinerules/](.clinerules/)** (6 ключевых файлов)
3. Изучить техническую архитектуру в **[rules/technical_architecture.md](rules/technical_architecture.md)**
4. Проверить актуальные задачи в **[rules/active_tasks.md](rules/active_tasks.md)**

### 2.2 Языковые Требования

- **ВСЕГДА** писать подробные комментарии в коде
- **НИКОГДА** не использовать транслитерацию

### 2.3 Обновление Документации
**ОБЯЗАТЕЛЬНО** обновлять ВСЕ необходимые документы:
- **[rules/active_tasks.md](rules/active_tasks.md)** - статус задач
- **[rules/progress.md](rules/progress.md)** - прогресс выполнения
- **[rules/technical_debt.md](rules/technical_debt.md)** - технический долг

## 3. Требования к Языку и Стилю

### 3.1 Код
- **Строгое соблюдение PEP8**
- **Обязательная типизация** (type hints)
- **SOLID принципы** во всех модулях
- **DRY (Don't Repeat Yourself)** - избегать дублирования кода
- **Fail-fast валидация** - ошибки должны выявляться максимально рано

### 3.2 Комментарии
- **ВСЕГДА** комментировать сложную логику на русском языке
- **ВСЕГДА** документировать на русском языке публичные функции и классы
- **ВСЕГДА** объяснять назначение модулей
- **ВСЕГДА** указывать автора изменений и дату

### 3.3 Документация
- **Markdown** формат для всех документов
- **Структурированный** подход с оглавлением
- **Ссылки** на связанные документы
- **Примеры** использования в документации API

## 4. Процесс Разработки и Документирования

### 4.1 Подготовка к Работе
1. Изучить существующую архитектуру
2. Проверить зависимости в **[rules/dependencies.md](rules/dependencies.md)**
3. Ознакомиться с паттернами в **[rules/systemPatterns.md](rules/systemPatterns.md)**
4. Проверить тестовую стратегию в **[tests/rag/TESTING_STRATEGY.md](tests/rag/TESTING_STRATEGY.md)**

### 4.2 Реализация
1. **Создать задачу** в **[rules/active_tasks.md](rules/active_tasks.md)**
2. **Реализовать** функционал с соблюдением стандартов
3. **Написать тесты** (unit, integration, e2e)
4. **Обновить документацию** параллельно с кодом

### 4.3 Завершение Работы
1. **Проверить** все тесты проходят
2. **Обновить** статус в **[rules/active_tasks.md](rules/active_tasks.md)**
3. **Создать** отчет о проделанной работе
4. **Обновить** технический долг в **[rules/technical_debt.md](rules/technical_debt.md)**

## 5. Стандарты Кода и Архитектуры

### 5.1 Архитектурные Принципы
- **RAG-as-a-Service** архитектура
- **Гибридный поиск**: dense (FastEmbed) + sparse (BM25 + кастомный sparse-энкодер)
- **CPU-first оптимизация** - GPU не требуется
- **Сервис ориентрованная архитектура** с четким разделением ответственности

### 5.2 Ключевые Компоненты
- **Jina v3 embeddings** (570M параметров) - **[JINA_V3_VM_MIGRATION_PLAN.md](JINA_V3_VM_MIGRATION_PLAN.md)**
- **Гибридный эмбеддер** - **[rag/embedder.py](rag/embedder.py)**
- **Векторное хранилище** - **[rag/vector_store.py](rag/vector_store.py)**
- **Поисковый сервис** - **[rag/search_service.py](rag/search_service.py)**

### 5.3 Файловая Структура
```
├── main.py                    # Точка входа
├── config.py                  # Конфигурация
├── rag/                       # RAG модули
│   ├── embedder.py           # Гибридный эмбеддер
│   ├── vector_store.py       # Векторное хранилище
│   └── search_service.py     # Поисковый сервис
├── parsers/                   # Парсеры кода
├── tests/                     # Тесты
├── rules/                     # Правила и документация
└── scripts/                   # Скрипты обслуживания
```

## 6. Правила Тестирования

### 6.1 Общие Требования
- **Offline/mock режим обязателен**
- **Все сетевые вызовы должны быть замоканы**
- **Строгая категоризация**: unit, integration, e2e, property-based
- **Property-based тесты** через `hypothesis`

### 6.2 Специфические Команды
```bash
# Запуск всех RAG тестов
pytest tests/rag/

# Специальный раннер для RAG модулей
python tests/rag/run_rag_tests.py

# Проверка offline режима
python tests/test_offline_no_network.py
```

### 6.3 Требования к Покрытию
- **Unit тесты**: минимум 90% покрытия
- **Integration тесты**: все критические пути
- **E2E тесты**: основные пользовательские сценарии
- **Property-based тесты**: edge cases и граничные условия

### 6.4 Mock Правила
См. **[rules/MOCKS_RULES.md](rules/MOCKS_RULES.md)** для детальных правил создания mock объектов.

## 9. Важные Напоминания

### 9.1 Обязательные Практики
- ✅ **ВСЕГДА** изучать документацию перед работой
- ✅ **ВСЕГДА** писать на русском языке
- ✅ **ВСЕГДА** комментировать код
- ✅ **ВСЕГДА** обновлять документацию
- ✅ **ВСЕГДА** следовать PEP8 + SOLID + DRY

### 9.2 Запрещенные Действия
- ❌ Не игнорировать существующие паттерны
- ❌ Не создавать технический долг без необходимости
- ❌ Не работать без понимания архитектуры
- ❌ Не пропускать этапы тестирования

### 9.3 Качество и Ответственность
- **Каждый агент несет ответственность** за качество своего кода
- **Все изменения должны быть обоснованы** и документированы
- **Технический дол должен минимизироваться** на всех этапах
- **Архитектурные решения должны согласовываться** с командой
